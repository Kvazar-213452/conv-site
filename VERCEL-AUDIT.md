# Аудит сумісності з Vercel — початковий стан

**Оновлення після адаптації:** 19 несумісних інструментів та SQLite-акаунти видалено. Залишилося 288 інструментів (67 серверних), 52 статті й 345 URL sitemap. Серверний trace зменшено з 441.20 до 143.24 MiB; input/output обмежено 4 MiB. Звичайний Next.js preset, Node 24, без Docker та beta. Актуальні інструкції — у VERCEL-DEPLOYMENT.md. Нижче збережено результати аудиту **до виправлень**, а не поточний стан.

Дата початкового аудиту: 2026-11-07. Висновок: поточний проєкт не можна вважати готовим до повного запуску звичайним Next.js-деплоєм на Vercel. Є несумісності з обробкою файлів, системними залежностями та зберіганням користувачів. Vercel Container runtime beta дає альтернативний шлях адаптації без обов'язкового перенесення всього сайту на інший хостинг.

Це аудит коду, локального production build і поточної офіційної документації. Реального Vercel preview, налаштувань акаунта, тарифу та runtime logs не перевірено. Попередні Docker-перевірки не підтверджують роботу на Vercel. У цьому аудиті код застосунку не змінювався.

## 1. Завеликий стандартний пакет функції

У `.next/server/app/api/convert/[slug]/route.js.nft.json` знайдено 2645 файлів залежностей, без відсутніх файлів. Сума розмірів унікальних реальних файлів — **441.20 MiB**. Найбільші: onnxruntime-node 293.32 MiB, tesseract.js-core 43.15 MiB, canvas native 35.08 MiB, Sharp libvips 17.83 MiB. Це розмір локального Next.js trace, а не остаточного Vercel artifact: пакування й платформа можуть змінити склад.

`next.config.ts:10` явно включає всі `onnxruntime-node/bin/**/*` і багато OCR/PDF assets до спільного endpoint. Навіть легкі конвертації отримують важкі залежності.

Стандартний ліміт Node.js Functions — 250 MB без стиснення. Поточний trace перевищує його. Важливий виняток: актуальна документація описує **Large functions beta до 5 GB**, з Fluid Compute та Active CPU; нові проєкти можуть бути eligible автоматично, для існуючих передбачено `VERCEL_SUPPORT_LARGE_FUNCTIONS=1`. Тому перевищення 250 MB не доводить неможливість будь-якого Vercel-деплою, але стандартний шлях має ризик відмови. Налаштування цього проєкту в акаунті невідомі.

Джерело: [Vercel Functions limits](https://vercel.com/docs/functions/limitations).

## 2. Системні рушії не встановлюються звичайним Next.js-деплоєм

`server/native-runtime.mjs:5` запускає `ffmpeg`, `ffprobe`, `libreoffice` і `.venv/bin/python`. Їх установку та Python requirements виконує Dockerfile. Next.js preset сам по собі не виконує цей Dockerfile і не створює Python venv.

17 інструментів останньої групи залежать від цих рушіїв:

- LibreOffice: `word-to-pdf`, `powerpoint-to-pdf`, `odt-to-pdf`.
- FFmpeg/FFprobe: `mp4-to-mp3`, `video-compressor`, `video-to-gif`, `video-trimmer`, `video-resizer`, `video-to-webm`, `audio-converter`, `audio-trimmer`, `audio-merger`, `audio-speed-changer`, `mute-video`, `video-frame-extractor`.
- Python/pypdf: `pdf-password-protect`, `pdf-unlock`.

`background-remover` та `pdf-compare` з цієї групи використовують Node/native бібліотеки; для них потрібна перевірка пакування, ABI, пам'яті та реального runtime. Решта 67 серверних інструментів теж потребують перевірки на Vercel після вирішення спільних обмежень. `worker_threads` сам по собі не є доказом несумісності.

**Актуальна альтернатива:** Vercel підтримує OCI-контейнери через Container runtime beta на всіх планах. Для вже визначеного Next.js-проєкту документація вимагає явно вибрати Container preset (`framework: container` або відповідне налаштування проєкту); наявності Dockerfile недостатньо. Наш Dockerfile встановлює потрібні рушії та слухає PORT=3000, але доступність beta, ліміти образу, порт/PORT, ресурси, cold start і реальний preview ще треба перевірити. Контейнер не робить локальні дані постійними.

Джерело: [Vercel Docker/container deployments](https://vercel.com/kb/guide/does-vercel-support-docker-deployments).

## 3. Файли 20 MiB не відповідають поточному HTTP-шляху

`server/conversions.mjs:21` дозволяє 20 MiB, `app/api/convert/[slug]/route.ts:7` — тіло запиту до 21 MiB. Клієнт надсилає multipart до функції та отримує результат як файл через ту саму функцію.

Документація Vercel Functions встановлює 4.5 MB на request/response body. Поточний шлях не має прямого завантаження в object storage чи окремого отримання результату. Великий upload може отримати 413 до виконання нашої перевірки; малий input теж може створити завеликий output. Container beta не слід вважати автоматичним обходом цього обмеження без перевірки її конкретного HTTP runtime.

Рішення: прямі підписані завантаження в object storage, завдання з ідентифікатором, отримання результату напряму зі storage. Для малих синхронних конвертацій — явні ліміти input/output із запасом на multipart.

Джерело: [Vercel payload limits](https://vercel.com/docs/functions/limitations#request-body-size).

## 4. SQLite та авторизація

`lib/db.ts:4` відкриває `process.cwd()/data.db`, одразу вмикає WAL і створює таблицю. `/api/user` імпортує цей модуль для реєстрації, входу й профілю. Звичайний runtime не надає постійної спільної файлової бази; запис у директорію застосунку також проблемний. Перенесення в `/tmp` не зберігає користувачів між інстансами й деплоями. Це залишається проблемою і в контейнері.

Потрібна зовнішня база даних та міграція запитів. Додатково `lib/auth.ts:5` має fallback для JWT_SECRET: у production треба обов'язковий власний секрет із environment, без відомого fallback. Значення environment акаунта цим аудитом не перевірялися.

Джерело: [SQLite on Vercel](https://vercel.com/kb/guide/is-sqlite-supported-in-vercel).

## 5. Навантаження та тривалість

`lib/server-conversion-runner.ts` обмежує два паралельні завдання лише всередині одного процесу. При масштабуванні це не глобальний rate limit чи черга. Worker heap 256 MB не обмежує всю нативну пам'ять FFmpeg/ONNX. Потрібні спільна черга/ліміти та перевірка пам'яті на реальних файлах.

`maxDuration=60`, локальні дедлайни 25/45 секунд і native timeout 30 секунд не є самостійним доказом несумісності з Vercel. Проте локальні швидкості не гарантують такого самого часу на доступних CPU під холодним стартом. Потрібен preview benchmark для обраного runtime.

## Рекомендований порядок адаптації

1. Вибрати явно: стандартний Next.js на Vercel + окремий сервіс конвертацій, або Vercel Container runtime beta з наявним Dockerfile після перевірки доступності та лімітів. Самої зміни таймауту недостатньо.
2. Винести користувачів у зовнішню постійну БД, налаштувати обов'язковий JWT_SECRET.
3. Впровадити прямі upload/download через object storage для великих файлів; додати чергу та спільні обмеження.
4. Для стандартного Next.js розділити легкі та важкі маршрути/залежності, звузити native tracing під Linux/потрібну архітектуру; перевірити остаточні Vercel function artifacts. Large functions beta вирішує лише питання розміру, не встановлює системні рушії.
5. Створити окремий Vercel preview, перевірити всі 86 серверних інструментів, реєстрацію/вхід після нового інстансу, файли біля HTTP-лімітів, результати більшого розміру, паралельність і cold start. Статичні сторінки та sitemap перевірити HTTP-запитами після деплою.

Зараз підтверджено працездатність локального/Docker середовища попередніми перевірками, але **повний запуск саме на Vercel ще не підтверджено**.
